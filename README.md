# Commenter

A small blog-style app where visitors browse posts and signed-in users like posts and hold threaded comment discussions.

Built with Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4, Drizzle ORM on MySQL, and Better Auth for email/password accounts.

## Features

- **Posts:** paginated list on the home page, detail page at `/<slug>` with image, breadcrumbs and a shared-element transition from the list.
- **Likes:** signed-in users can like and unlike posts and comments.
- **Comments:** create, edit and delete your own comments, reply to any comment (replies nest without limit), sort the thread.
- **Auth:** register and log in with email and password at `/register` and `/login`. Registration requires accepting the user agreement at `/terms`. Sessions are cookie based and handled by Better Auth under `/api/auth/*`.
- **Profile:** `/profile` shows your comment history; `/profile/settings` lets you upload or remove a profile picture, change your name, email and password, and delete your account (comments, likes and picture go with it). Pictures are stored in the database and served from `/api/avatars/<userId>`.
- **Responsive layout:** header with user menu, mobile hamburger menu, loading skeletons on every data-driven page.

## Architecture

Code is organised by feature, and each feature has three layers:

| Layer | Folder | Responsibility |
|---|---|---|
| Presentation | `features/<feature>/presentation` | Components, server actions, form state |
| Domain | `features/<feature>/domain` | Entities, use cases, repository interfaces, errors. Pure TypeScript, no framework imports |
| Data | `features/<feature>/data` | Drizzle repositories and row-to-entity mappers |

Each feature's `di.ts` wires repositories into use cases, and `app/` contains only thin pages that compose feature components.

```
app/                      # Routes: /, /[slug], /login, /register, /api/auth/[...all]
features/
  auth/                   # Register, sign in, sign out, current user
  comments/               # Threaded comments, edits, likes
  posts/                  # Post listing, detail, likes
  profile/                # Comment history, profile picture, credentials, account deletion
  users/                  # Legacy seeded users (comment authors from the seed script)
shared/                   # Header, footer, UI primitives, pagination and error types
lib/                      # Better Auth server and client config
drizzle/
  src/db/                 # Drizzle client, schema, seed script
  migrations/             # SQL migrations generated by drizzle-kit
```

## Prerequisites

- Node.js 20.9 or newer (developed on Node 24)
- npm
- A MySQL-compatible database: a local MySQL 8 server, or a hosted [TiDB Cloud](https://tidbcloud.com) cluster (see [Using TiDB Cloud](#using-tidb-cloud))

## Running locally

### 1. Install dependencies

```bash
npm install
```

### 2. Configure environment variables

Create a `.env.example` file in the project root with the variables below (it is gitignored, so each developer keeps their own):

```dotenv
DATABASE_HOST=localhost
DATABASE_PORT=3306
DATABASE_USERNAME=root
DATABASE_PASSWORD=
DATABASE_NAME=commenter
DATABASE_SSL=false

BETTER_AUTH_SECRET=        # openssl rand -base64 32
BETTER_AUTH_URL=http://localhost:3000
```

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_HOST` | Yes | MySQL host. The app throws on startup if it is missing |
| `DATABASE_PORT` | No | MySQL port. Defaults to 3306. TiDB Cloud uses 4000 |
| `DATABASE_USERNAME` | Yes | MySQL user |
| `DATABASE_PASSWORD` | Yes | MySQL password (may be empty for a local root user) |
| `DATABASE_NAME` | Yes | Database name. Create it first: `CREATE DATABASE commenter;` |
| `DATABASE_SSL` | No | Set to `true` to connect over TLS (required by TiDB Cloud). Off by default |
| `BETTER_AUTH_SECRET` | Production | Signs session cookies. In development Better Auth falls back to a default and logs a warning |
| `BETTER_AUTH_URL` | No | Base URL of the app. Inferred from the request when omitted |

Both the runtime client (`drizzle/src/db/index.ts`) and `drizzle.config.ts` build their connection from these variables through `drizzle/src/db/connection.ts`, so they always point at the same server.

**Which file is read:** Next.js loads `.env.example` on its own. The CLI scripts (`drizzle-kit` and `npm run db:seed`) load variables through `dotenv/config`, which only reads `.env` by default. Either keep a `.env` with the same values, or point dotenv at the local file as shown in the commands below. All `.env*` files are gitignored.

### 3. Create the database schema

The first migration is a baseline no-op, so on a fresh database push the schema directly from the Drizzle definitions:

```bash
DOTENV_CONFIG_PATH=.env.example npx drizzle-kit push
```

This creates the `users`, `post`, `comments`, `post_like` and `comment_like` tables plus the Better Auth tables (`user`, `session`, `account`, `verification`).

If you already have a database created before the likes-and-comments work, apply the pending migration instead:

```bash
DOTENV_CONFIG_PATH=.env.example npx drizzle-kit migrate
```

### 4. Seed sample data (optional)

```bash
DOTENV_CONFIG_PATH=.env.example npm run db:seed
```

Seeds 100 users, 100 posts and 200 comments with deterministic data. The script clears the `comments`, `post` and `users` tables first, so do not run it against data you want to keep. Seeded users live in the legacy `users` table and cannot log in; register an account through the UI to like or comment.

### 5. Start the dev server

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

## Using TiDB Cloud

TiDB Cloud is MySQL-compatible, so the app, Drizzle and Better Auth work unchanged. Only the connection settings differ.

1. Create a cluster at [tidbcloud.com](https://tidbcloud.com) (the Starter/Serverless tier is free) and create a database named `commenter` from the SQL editor, or let `drizzle-kit push` run against the default `test` database and set `DATABASE_NAME=test`.
2. In the cluster overview click **Connect**, choose **General** / **Node.js**, and generate a password. Copy the host, port, and user shown there.
3. Set the variables:

```dotenv
DATABASE_HOST=gateway01.<region>.prod.aws.tidbcloud.com
DATABASE_PORT=4000
DATABASE_USERNAME=<prefix>.root
DATABASE_PASSWORD=<generated password>
DATABASE_NAME=commenter
DATABASE_SSL=true
```

TiDB Cloud rejects plain connections, so `DATABASE_SSL=true` is mandatory. The connection verifies the server certificate against the system trust store (TLS 1.2 or newer); no CA bundle needs to be downloaded.

4. Push the schema and seed as in steps 3 and 4 above.

Notes:

- The username keeps the `<prefix>.` part. It tells the TiDB Cloud gateway which cluster you are connecting to.
- Serverless clusters pause after a period of inactivity. The first query after a pause takes a few seconds while the cluster resumes.
- Set the same six variables in your hosting provider (for example in the Vercel project's Environment Variables) for production deployments.
- TiDB rejects `DEFAULT (now())` on `timestamp(3)` columns, which is what Drizzle's `.defaultNow()` emits. The schemas therefore use `.default(sql`CURRENT_TIMESTAMP(3)`)`, which both MySQL 8 and TiDB accept. Keep using that form for new timestamp columns.

## Scripts

| Command | What it does |
|---|---|
| `npm run dev` | Start the Next.js dev server |
| `npm run build` | Production build |
| `npm start` | Serve the production build |
| `npm run lint` | Run ESLint |
| `npm test` | Run the Vitest suite once |
| `npm run db:seed` | Reset and seed the database with sample data |

Database schema commands go through `drizzle-kit` directly: `generate` to create a migration from schema changes, `migrate` to apply pending migrations, `push` to sync the schema without a migration, `studio` to browse the database.

## Testing

```bash
npm test
```

Tests live in `features/<feature>/__tests__/` and `shared/__tests__/`, mirroring the three layers. Domain tests use in-memory fake repositories, so the suite needs no database or network.

## Git workflow

Work happens on `feature/<feature-name>` branches, never directly on `main`. Commit each unit of work once its tests pass.
